# ADR-0004: Incremental sync via `pts`, not `last_message_id`

**Status:** accepted (2026-08-20)

## Problem
An OSINT archiver must observe **edits and deletions**, not just new messages.
Resuming by "highest message id seen" (what most prior-art tools do) can never
see an edit or a deletion.

## Decision
Sync on the channel's `pts` (the per-channel event counter). Seed from
`channelFull.pts`; each run calls `updates.getChannelDifference(pts)` to receive
new messages **plus** `updateEditChannelMessage` and
`updateDeleteChannelMessages`. Messages are **versioned** (`message_revisions`,
append-only, keyed by content hash); deletions are **tombstones** with an
evidence rank: `update` (unambiguous) > `empty` (`messageEmpty` for an id inside
a previously verified-complete range) > `gap` (never observed; may be
hidden/service). `deleted_at` is set only for `update`/`empty`. Counters
(views/forwards/replies/subscribers) carry no `pts` and are snapshot-only →
`message_metrics` / `channel_snapshots` time series.

## Consequences
- The pts window (~100k events) bounds after-the-fact deletion recovery; the
  `watch` loop and web/Wayback snapshots complement it.
- `channelDifferenceTooLong` triggers a pts re-seed + gap probe.
- Pre-edit bodies exist only if captured first (server keeps none for
  non-admins), which is exactly what `message_revisions` provides.
